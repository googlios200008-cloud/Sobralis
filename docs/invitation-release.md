# Приглашения: подготовка совместимости для релиза

## Что меняется

Приглашение — секрет, владение которым может дать доступ. Не публикуйте настоящие ссылки и токены в логах, скриншотах, тикетах, аналитике или переписке с поддержкой. Данные во фрагменте URL обычно не отправляются серверу при открытии, но их может получить другое приложение, браузер, расширение, JavaScript, история устройства и получатель ссылки.

Текущий API для создания приглашения в поездку возвращает ссылку вида `/#trip-invite=…`, как и интерфейс. Прежде API возвращал `/join/…`, а UI преобразовывал ссылку. Новый UI проверяет origin, отсутствие учётных данных и параметров, формат и понимает оба ответа; старый UI, ожидавший `/join/…`, новый ответ может не понять. Ссылка сообщества также использует фрагмент. Текущие экраны предварительного просмотра и принятия отправляют токен в JSON-теле, а не в пути или query. Тела и ответы тоже содержат секреты и не должны попадать в журналы.

В `NODE_ENV=production` старые API-маршруты `GET .../:token/preview` и `POST .../:token/redeem` для обоих типов приглашений **не регистрируются** и отвечают 404. В development/test они сохранены только для совместимости и тестирования, без ослабления проверки прав. Наличие этой ветки не означает, что действующий demo уже обновлён. Существующие ссылки с фрагментом и текущие клиенты остаются совместимыми; старые приложения, которые используют пути с токенами или ожидают старый ответ API, должны быть обновлены. Не переключайте сервер поверх неготового frontend: новая форма повтора встреч тоже требует совместимого API и схемы. Нужны окно обслуживания, доставка согласованных версий и тестирование с кэшами. Откат к старой версии должен предусматривать проверенный план схемы и совместимости.

Серверный отказ не защищает от записи уже пришедшего старого адреса у входного TLS-прокси, CDN, браузера или сторонних средств. Отключите сбор полного URL и тел либо обеспечьте проверенную редактирующую политику на **каждом** компоненте до обработки запроса; также откажитесь от устаревших клиентов. Защита запросов в журнале backend не означает, что остальные компоненты безопасны.

## Проверки

`backend/tests/legacy-invites.test.ts` проверяет отказ обеих старых операций в production, работу body-preview, независимость от введённой переменной среды и сохранение тестового режима. `tests/run-invitations-live.py` при явном opt-in последовательно создаёт **новую** `sobralis_invitations_test` для каждого из пяти PostgreSQL тестов приглашений, участия и отмены поездки; если имя занято, тест не удаляет БД. После успешного создания каждого временного экземпляра он удаляется в `finally`. Нужны тестовые учётные данные к отдельному тестовому кластеру; не указывайте production.

`tests/run-android-https-live.py` на отдельной БД проверяет актуальные потоки обоих приглашений через временный HTTPS/gateway, работу нового fragment-ответа и преобразование синтетически подменённого старого ответа, без передачи токенов в сетевых URL. Сертификат искусственно закреплён, в тесте повышен лимит входов: это не проверка Android WebView, реального TLS, журналов инфраструктуры, распределённого ограничения запросов или независимый аудит.
