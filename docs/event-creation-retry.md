# Повтор создания встречи

Миграция `0032` и API добавляют необязательный `clientRequestId` (UUID) к созданию встреч сообщества и поездки. При повторе запроса **одним аккаунтом** с тем же ключом и тем же нормализованным содержимым возвращается та же встреча; одновременные повторы сериализуются в PostgreSQL. Клиент должен сохранить ключ до отправки и повторять именно его, не создавая новый после неопределённого ответа. Разные ключи намеренно могут создавать одинаковые встречи.

Ключ охватывает тип и ID сообщества/поездки, название, описание, место, момент времени, часовой пояс, тип места, ночёвку и её вместимость, гостей, алкоголь и еду. API применяет существующую нормализацию; время сравнивается как момент в UTC независимо от временной зоны SQL-сессии. Повтор с изменёнными параметрами возвращает `409 EVENT_REQUEST_CONFLICT`. Для успешной первоначальной отправки и корректного повтора API возвращает `201` с текущим представлением той же встречи: если её позже отредактировали, это уже изменённые данные. Актуальность хозяина вычисляется заново.

Повтор не является правом доступа. Сервер заново проверяет подтверждённого активного пользователя, действующее участие, доступность сообщества и поездки и отсутствие отмены встречи. При потере доступа или отмене возвращается `404`; права не восстанавливаются и новая встреча не создаётся. Действующий участник, пониженный до наблюдателя, может получить уже созданную и доступную ему встречу, но не создать новую. Неуспешная первичная проверка прав или корректности не резервирует ключ. Запись результата и сама встреча создаются в одной транзакции.

Таблица ключей закрыта от прямого доступа runtime. Она хранит SHA-256 нормализованного запроса, а не вторую открытую копию названия, описания и места; это **не шифрование** и короткие предсказуемые значения потенциально угадываются. Тексты самой встречи по-прежнему хранятся в базе. Не следует журналировать тела запросов, чувствительные данные или SQL-параметры. Срок хранения записей повторов ещё не определён; политика хранения, удаление и взаимодействие с резервными копиями — отдельные задачи до запуска. При физическом удалении встречи или аккаунта связанная запись ключа удаляется; после этого повтор может снова создать встречу. Обычная отмена мягкая и ключ сохраняет.

Формы сообщества и поездки используют `clientRequestId`. Перед отправкой интерфейс сохраняет попытку отдельно для каждого аккаунта и вкладки в `sessionStorage`: ID аккаунта и области, название, локальное время, момент UTC, часовой пояс и случайный ключ. Эти данные **не зашифрованы**, доступны скриптам того же origin и обычно пропадают при закрытии вкладки; другой браузер, устройство или вкладка не гарантируют доступ к ним. При открытии вкладки из другой браузер может скопировать исходное `sessionStorage`; это не межвкладочная синхронизация. Не вводите личные данные в общий demo. Выход из аккаунта сам по себе не стирает ключ; при возвращении в аккаунт можно продолжить проверку.

Для одного аккаунта во вкладке допускается только одна неподтверждённая попытка создания встречи независимо от типа области. При неопределённом ответе вернитесь к прежней компании или поездке и повторите с исходным названием и временем; исходные часовой пояс, UTC и ключ сохранятся. Если в форме остался другой текст, вручную введите значения из предупреждения: интерфейс не перезаписывает непустые поля. Одновременная отправка блокируется. Ответы старого аккаунта не меняют новый экран; повторно войдя, проверку можно продолжить.

При потере доступа или повреждённой сохранённой записи отдельная кнопка доступна вне формы. Она требует подтверждения и забывает ключ, но **не доказывает отсутствие встречи и не отменяет уже отправленный запрос**. Сначала проверьте все доступные страницы списка и, если нужно, попросите других участников проверить встречу; повторное создание с новым ключом может дать дубль. При ошибке удаления уже сохранённого ключа интерфейс сохраняет предупреждение и не разрешает новую попытку. Если хранилище вкладки недоступно, попытка живёт лишь в памяти страницы: повторите до перезагрузки; после неё сначала проверьте список, поскольку восстановление ключа не гарантируется. Вкладка может быть закрыта или очищена, запрос может завершиться позже; защита не абсолютна. Из-за задержки ответа сервер может вернуть неопределённый результат даже после потери доступа. Опросы, приглашения и другие операции не охватываются.

Миграция протестирована на отдельных синтетических БД и в PGlite. Действующий demo с миграцией `0031` специально не обновлялся: перед его обновлением нужны свежая закрытая копия, восстановление в отдельную БД, сравнение данных, затем согласованный запуск новой схемы и API. Новый API с проверкой готовности не запустится на старой схеме `0031`. Сначала в согласованном окне применяется миграция, затем запускается совместимый API и проверяется `/ready`; только после этого можно подключать клиент, посылающий новое поле. Откат требует отдельного проверенного плана; неизменяемые миграции нельзя редактировать после применения.

`tests/run-event-once-live.py` создаёт и удаляет только новую явно разрешённую одноразовую БД `sobralis_event_once_test`. Проверяются параллельные повторы, различия содержимого, два типа области, ограничения доступа, отмена, сохранение старого API и независимость от временной зоны SQL-сессии. `tests/run-schema-readiness-live.py` и backend unit/PGlite проверяют совместимость подготовленной схемы. Синтетический HTTPS тестирует обе формы в Chromium и API напрямую: после записи тестовый прокси подменяет ответ на 503, затем повторяется тот же ключ и проверяется одна встреча. Также проверяются перезагрузка, другая область/аккаунт, задержанный ответ, повторный submit, недоступное хранилище, повреждённая запись и подтверждение забывания. Это не реальный обрыв соединения и не Android WebView. В этом изолированном тесте лимит входов повышен из-за множества логинов с одного loopback IP; проверка rate limit в него не входит. Ничто из этого не подтверждает production-развёртывание или независимую проверку безопасности.
