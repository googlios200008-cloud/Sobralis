# План переноса локальных данных прототипа

Состояние: **план, не реализация импорта**. Никакие данные из браузера автоматически на сервер не передаются.

## Что есть сейчас

- `localStorage.sobralis-v2` содержит группы, локальные ID и имена участников, графики по дням, встречи, опросы, записи и переписку. Некоторые записи и люди демонстрационные.
- JSON-файл из раздела «Резервная копия» содержит те же данные в формате `sobralis-local-backup` версии 1. Он не зашифрован; его нельзя размещать публично.
- Имя или локальный ID не подтверждает, что человек является владельцем конкретного серверного аккаунта. Нельзя автоматически создавать реальные аккаунты на основе имени или сопоставлять людей по совпадению имён.

## Предпосылки

1. Реальная регистрация, подтверждение email, сессии и приглашения в сообщество должны быть безопасно реализованы и юридически проверены; пользовательские документы и способы связи с оператором готовы.
2. Владелец данных скачал локальную копию и отдельно проверил восстановление. На сервере есть резервное копирование и проверка восстановления. Импорт и локальная копия не заменяют друг друга.
3. Явно выбраны компания, учётная запись инициатора, часовой пояс каждой встречи, цели и объём переноса. Перенос выполняется только после аутентификации и понятного подтверждения.
4. Для личных чатов, сведений о самочувствии и других потенциально чувствительных данных сначала определены законные основания, круг получателей и сроки хранения. До этого такие записи остаются только локальными.

## Предполагаемый безопасный процесс

1. Локально разобрать и проверить файл, ограничить размер и вложенность, показать содержание и ошибки без загрузки лишних сведений на сервер. Демонстрационные записи должны быть явно помечены для исключения пользователем; не угадывать их принадлежность.
2. Показать предварительный отчёт (dry run): сколько групп, событий и личных записей может быть перенесено, что будет пропущено, какие даты и связи неоднозначны. Исходный файл не изменять.
3. Сопоставить локального владельца с **текущей подтверждённой сессией**. Для каждого другого участника — отдельное приглашение и согласованное подтверждение самим участником. Пока сопоставления нет, его график и голос не записываются под чужим аккаунтом.
4. Дату графика сохранять как `DATE` без перевода между часовыми поясами. Локальные дата и время встречи превращать в UTC только после явного выбора IANA-часового пояса; при неоднозначном или несуществующем местном времени пользователь должен принять решение.
5. После подтверждения выполнять импорт в транзакциях с устойчивым ключом идемпотентности. Повторная отправка не должна дублировать сущности. Ошибки показывать без записи содержимого переписки и ПДн в логи.
6. Созданные записи показывать как результат импорта; не перезаписывать существующие данные других участников. Дать способ отменить импорт в пределах отдельно определённого срока хранения.
7. Проверить результат по количеству и связям, сохранить понятный отчёт для пользователя. Не удалять ни локальные данные, ни файл без отдельного решения пользователя.

Точный порядок согласий, проверка владельца архивов, поведение при отзывах, сроки удаления и порядок обработки чувствительных данных требуют юридического и security-review до реализации.
