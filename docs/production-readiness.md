# Подготовка к production: статус и порядок работ

Этот документ — рабочий план, не подтверждение готовности к выпуску. Разработанная оболочка — автономный Android-прототип; подключённый Android-прототип ограничен адресами `.test`. Действующих production-домена, инфраструктуры, оператора данных и релизного ключа в проекте не задано. Планируется первый релиз с текущими функциями для Android, iOS и веба и международной аудитории; магазины, сервер и домен пока не выбраны. Отдельного iOS-приложения ещё нет; см. [дорожную карту](release-roadmap.md). Не использовать демостенд для реальных персональных данных и не снимать блокировки production-регистрации или восстановления до устранения причин.

## Выполненная техническая защита запуска

- API требует явный `NODE_ENV`; при отсутствии не запускается в неявном development-режиме. Dockerfile задаёт production явно. В production включение регистрации и восстановления пока намеренно отклоняется.
- Миграция `0031` предоставляет runtime-роли только чтение списка имён и контрольных сумм миграций через узкую SQL-функцию. Прямой доступ к таблице истории не добавлен. На старте API сверяет точный состав и SHA-256 миграций образа с БД и отказывается слушать порт при несовпадении или недоступности БД. `/ready` повторяет проверку; `/health` отражает лишь работу процесса. Ошибки в ответах и стартовом журнале не раскрывают содержимое БД или секреты. В Compose healthcheck API использует `/ready`.
- Перед обновлением синтетического demo создан backup до `0031`; проверены восстановление и неизменность данных 39 существовавших таблиц. Backup защищён правами файла, но **не зашифрован**; это не production-система резервирования. API demo перезапущен на новой схеме, сохранены существующие сообщества и графики.
- Подготовлен потоковый компонент [шифрования копий PostgreSQL](encrypted-database-backup.md); синтетическая копия расшифрована и восстановлена отдельно. Ключ оператора, расписание, защищённое внешнее хранилище и наблюдение ещё не настроены — это не готовая система резервирования.
- Gateway и локальная Android-оболочка запрещают inline-скрипты; локальные встроенные обработчики заменены фиксированным диспетчером, стили в оболочке всё ещё требуют `unsafe-inline`. Сценарии и блокировка встроенного кода проверены в Chromium и синтетическом HTTPS. Это частичная защита, не доказательство отсутствия XSS; реальный Android WebView и обновление на устройстве не проверены.
- Дополнительно закрыты некоторые пути внедрения разметки из повреждённого localStorage: идентификаторы участников экранируются в списках, неизвестные статусы графика отображаются как неотмеченные без изменения сохранённого значения. Сценарии проверены на специально изменённых данных в отдельном Chromium-профиле. Это точечная проверка, не полный аудит; стандартный JSON-экспорт может отклонить повреждённое состояние.
- При явно нечитаемом или несовместимом базовом состоянии локального хранилища теперь блокируются обычные записи и предлагается отдельный незашифрованный аварийный файл с исходной строкой. [Ограничения и действия](local-storage-recovery.md): это не штатная копия и не автоматическое восстановление, вложенные повреждения и конкурирующие вкладки не охвачены; проверено только в изолированном Chromium.
- Для локальных вкладок добавлена [оптимистическая проверка устаревших данных](local-tab-conflicts.md): обычные последовательные конфликты останавливают сохранение и позволяют скачать состояние вкладки. Сравнение и запись не атомарны; одновременная гонка и устаревшие версии приложения всё ещё могут перезаписать данные. Нужны транзакционная модель и испытания на устройстве.
- [Повтор создания встреч](event-creation-retry.md) подготовлен в API и интерфейсе и проверен на изолированных данных, но действующий demo остаётся на старых API и схеме `0031`. Его прежние формы не используют ключ и могут создать дубль. Обновление требует отдельной проверки резервной копии и согласованного развёртывания схемы, API и клиента; защита повтора ограничена сохранностью ключа.
- [Готовность и минимальная диагностика](release-diagnostics.md): API при обнаруженном несовпадении схемы отвечает 503 до запуска обработчика API, и `/ready` тоже становится 503. Проверяется журнал миграций, но не целостность таблиц, функций или данных; запрос уже может выполняться, когда схема меняется. Это не заменяет остановку трафика, readiness-aware маршрутизацию, нагрузочную проверку и согласованное обновление. Прямой доступ к API следует закрыть. Для отладки есть случайные ID запросов и ограниченные opt-in сигналы без содержимого; готовой системы наблюдения и защищённого хранения журналов нет.

- В подготовленной ветке production API не регистрирует старые маршруты приглашений с токеном в пути; ссылка на поездку теперь сразу возвращается с токеном во фрагменте. Новый интерфейс понимает и прежний ответ сервера, но старый интерфейс несовместим с новым API. Действующий demo не переключали; необходимо согласованное обновление. Внешние прокси по-прежнему могут записать полученный от старого клиента URL до отказа. Синтетические PostgreSQL и HTTPS-тесты не заменяют проверку инфраструктуры и клиентов.

## Блокеры публичного запуска

1. **Доставка и среда.** Определить владельца, домен, где и кем размещается сервис, DNS, защищённый TLS reverse proxy, реальные сертификаты, разделение доступа и способ доставки релизов. Проверить Compose/сеть на выбранной среде и почтовый выход: sandbox не является инфраструктурой для пользователей. Релизный gateway сейчас слушает только loopback и сам не завершает TLS.
2. **Безопасность.** Провести независимую проверку динамического HTML, диспетчера действий, XSS, авторизации, сессий и приглашений; по возможности убрать зависимость оболочки от inline-стилей и проверить CSP в реальном Android WebView. Production API не регистрирует старые маршруты с токеном в URL; старые клиенты несовместимы, а прокси и журналы могут сохранить старый входящий URL ещё до отказа, поэтому необходима надёжная фильтрация. Реализовать защиту от перебора и перегрузки с достоверным IP и общей политикой для нескольких экземпляров, без доверия к поддельным заголовкам. Проверить угрозы клиентам и серверу.
3. **Аккаунты и почта.** Подтверждение email и восстановление уже имеют тестовые сценарии, но production-флаги заблокированы. Нужны реальная проверенная доставка SMTP и исходящей сети, политика паролей, жизненный цикл сессий, уведомления и процессы поддержки. Документы и законное основание должны быть утверждены ответственными до включения.
4. **Данные и эксплуатация.** Зашифрованные регулярные резервные копии отдельно от основного сервера, хранение ключей, политика и испытания восстановления, мониторинг и инциденты. Нужны управляемые сроки хранения, экспорт и полный жизненный цикл удаления аккаунтов и данных, включая копии и журналы; soft-delete не является уничтожением. Продумать миграцию локальных данных без автоматического сопоставления людей.
5. **Мобильные платформы.** Отдельного приложения iOS пока нет; требуются архитектура, подпись, сборки, реальные устройства и проверка актуальных требований App Store. **Android:** Реальный подключённый релиз не создан: адрес `.test`, экспериментальный WebView и тестовый ключ не являются релизом. Нужны решение о распространении, защита релизного ключа, версии и обновления с сохранением пользовательских данных, Android App Links, реальные доверенные HTTPS/cookie и тесты на устройствах, включая доступность, системные диалоги и восстановление после прерываний.
6. **Правовые и организационные решения.** Ответственный оператор, юрист и специалист по защите данных должны определить цели, основания и сроки обработки, права субъектов, подрядчиков и фактическое размещение, подготовить и проверить необходимые документы и процессы. Соответствие законам и требованиям магазина не подтверждено.

## Проверки

`tests/run-schema-readiness-live.py` с явным `ALLOW_DISPOSABLE_DATABASE=yes` создаёт только отдельную БД `sobralis_schema_readiness_test`, применяет миграции, запускает настоящий API-процесс, проверяет отказ без режима и при несовпадении, 503 у `/ready`, отсутствие секретов в ответе и восстановление готовности. БД удаляется; если имя занято, тест останавливается. Требуются тестовые `DB_HOST`, `DB_PORT`, `TEST_ADMIN_PASSWORD`, `TEST_MIGRATOR_PASSWORD`, `TEST_RUNTIME_PASSWORD`; никогда не направлять его в production-кластер. Unit/PGlite-тесты дополнительно проверяют ограничения доступа и неизменность данных. Конфигурация Compose проверена статически, но реальный Docker daemon в данной среде не работает — это не проверка развёртывания.

После реализации блокеров нужны отдельные интеграционные, нагрузочные и восстановительные испытания, ревизия безопасности, юридическая проверка и приёмочные испытания на настоящих устройствах и целевой инфраструктуре. Одни автоматические тесты не означают готовности к production.
