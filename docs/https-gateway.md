# Подготовка HTTPS-маршрутизации

`infra/site-gateway.cjs` — новый отдельный gateway исходного интерфейса и API. Он **не является HTTPS-сервером**: слушает только `127.0.0.1` и не должен напрямую публиковаться в интернет. Настоящих домена, сервера, TLS-сертификата, оператора, мониторинга и проверенной production-конфигурации пока нет. Этот компонент не делает приложение или регистрацию готовыми к запуску.

Gateway принимает только точный Host заданного HTTPS-origin, предоставляет явно перечисленные файлы исходной оболочки и сопоставляет `/verify-email` и `/reset-password` со страницами регистрации и восстановления. `/api/` проксируется на фиксированный порт API на `127.0.0.1`; другие произвольные файлы и адреса не открываются. Cookie и Origin проходят к API без demo bearer-моста; поддельные `Forwarded`, `X-Forwarded-*`, `X-Real-IP` и `X-Demo-Session` удаляются. Максимум тела API — 16 КБ, в том числе при chunked-загрузке. Заголовки запрещают встраивание в iframe и передачу Referer. Для всех страниц gateway запрещает inline-скрипты (`script-src 'self'`); отдельные страницы входа, регистрации и восстановления также запрещают inline-стили. Основной `index.html` всё ещё требует `unsafe-inline` для стилей. Обработчики локального интерфейса заменены фиксированным диспетчером без выполнения строк как кода. Это не доказывает отсутствия XSS: страницы на одном origin, HTML строится динамически и требует независимой проверки. Ответы не кэшируются; производительность и кэширование ещё требуют доработки.

Для будущего развёртывания TLS должен завершаться **отдельным проверенным reverse proxy** перед gateway. Он обязан принимать только целевой домен, передавать канонический `Host` (без неявного `:443`), правильно отклонять неизвестные имена, не записывать в логи токены, cookie, пароли и тела запросов, а также закрывать административные порты и защищать ключи сертификата. ACME challenge и перенаправление HTTP→HTTPS относятся к TLS-прокси, не к gateway. Локальный порт gateway не должен быть доступен недоверенным процессам или контейнерам. Требуются заголовки и лимиты на внешнем прокси, контроль времени и размера запросов, мониторинг, обновления, отказоустойчивость и проверка всей цепочки. Нельзя принимать `Forwarded` от клиента как достоверный.

Обновлённый интерфейс отправляет секреты приглашений только в JSON-теле `POST /api/community-invites/preview|redeem` и `POST /api/invites/preview|redeem`: это уменьшает риск утечки через журналы URL, но не защищает от логирования тел или ответов, мониторинга, браузерных расширений и XSS. В режиме production сервер не регистрирует старые API-маршруты с токеном в пути; в test/development они сохранены для проверок совместимости. Старые клиенты, использующие эти маршруты, перестанут работать с production API: сначала нужно обновить клиентов и проверить совместимость. Для поездок API теперь сразу возвращает ссылку `/#trip-invite=…`; прежний формат `/join/…` в ответе API больше не возвращается. Новый интерфейс принимает оба формата ответа старого и нового сервера, но прежний интерфейс, ожидавший только `/join/…`, несовместим с новым API. Уже показанные пользователям ссылки с фрагментом не меняются. Для существующих клиентов необходимо согласованное обновление в окно обслуживания и проверка кэша, а не независимое переключение frontend и API. Отказ backend не предотвращает запись старого адреса входным TLS-прокси, CDN или журналами до отказа — фильтрация по-прежнему обязательна. В test/development обе версии операции делят один процессный лимит; распределённого ограничения нет. Новый сервер и интерфейс необходимо выпускать согласованно.

Проверять готовность backend через `/ready`, а не только `/health`: после миграции `0031` `/ready` сверяет журнал миграций с релизом. Gateway сам не снимает неготовый API с маршрутизации. API проверяет журнал миграций непосредственно перед обработчиками и при обнаруженном несоответствии отвечает 503; проверка не атомарна с обработкой, поэтому внешний маршрутизатор и остановка трафика при миграции всё равно необходимы. Подробности и ограничения: `production-readiness.md`.

API сейчас не доверяет произвольным proxy-заголовкам; поэтому за gateway все запросы выглядят пришедшими с loopback и частотные лимиты разделяются всеми клиентами. Это безопаснее подмены IP, но непригодно для нагрузки и не заменяет проверенную распределённую защиту до запуска. Production-регистрация и восстановление по-прежнему заблокированы в конфигурации сервера, и письма с реальным провайдером не проверены. Compose с `internal` сетью не обеспечивает исходящий SMTP. Не использовать реальные пользовательские данные до решения этих и юридических вопросов.

Для локальной разработки с уже запущенным **синтетическим** API можно указать одинаковый `PUBLIC_ORIGIN` в API и gateway и запустить, например:

```sh
PUBLIC_ORIGIN=https://sobralis.example.test API_PORT=8081 GATEWAY_PORT=4180 node infra/site-gateway.cjs
```

Это откроет только HTTP на loopback: пример не включает TLS и не создаёт публичный сервер. Адрес `.test` условный, DNS и доверенный сертификат не настроены. Gateway не загружает тестовые аккаунты и не знает их пароль.

`node --test tests/site-gateway.test.cjs` проверяет маршруты, точный Host, отклонение путей и методов, заголовки, удаление поддельных proxy-заголовков, передачу cookie и ограничение тела. `tests/run-android-https-live.py` дополнительно запускает этот gateway за временным TLS-терминатором и проверяет оригинальный интерфейс, real HttpOnly-cookie, CSRF/Origin, семейное делегирование, приглашения в сообщество и поездку, запрет встроенного скрипта на отдельной странице входа, закрытые маршруты восстановления с одноразовой БД. Сертификат в Chromium закреплён искусственно для теста; стандартное доверие к TLS, Android WebView, настоящий TLS-прокси и production Compose этим не проверены. Условия и ограничения теста: `android-connected-test.md`.

Переход на CSP требует согласованной публикации `index.html`, всех его скриптов и gateway одной версией: старая оболочка с inline-обработчиками при новой политике будет неработоспособна. Версии изменённых файлов в HTML повышены; gateway отдаёт `no-store`. Не следует переключать политику отдельно от файлов приложения или считать эти меры заменой испытания обновления в целевом окружении. Диспетчер принимает идентификаторы формата существующего импорта (`A–Z`, `a–z`, `0–9`, `_`, `-`, не более 80 символов); повреждённые или нестандартные идентификаторы, ранее оказавшиеся непосредственно в localStorage, могут стать недоступны для действий. Данные при этом не удаляются. Обычный экспорт и импорт JSON проверяют структуру и могут отклонить такие данные: до очистки или восстановления необходимо сохранить оригинал хранилища доступным способом, без автоматического исправления или перезаписи.
