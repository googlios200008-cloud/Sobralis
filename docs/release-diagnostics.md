# Минимальная диагностика API и проверка готовности

Это строительные блоки отладки, **не готовая система мониторинга** и не подтверждение безопасности или соответствия требованиям законодательства. Действующий demo ими не обновлён. В продакшене требуются владелец эксплуатации, защита и ограничение доступа к журналам, политика сроков хранения, оповещения, проверка всей цепочки прокси и отдельная оценка рисков обработки данных.

## Корреляция и журналы

Для ответов `/api/` backend создаёт новый случайный UUIDv4 и возвращает `X-Request-Id`. Клиентский заголовок с таким именем **не используется** как идентификатор сервера. Повтор запроса получит новый ID: это не ключ идемпотентности и не позволяет находить другие попытки автоматически. Если ошибка произошла до приложения (TLS, внешний прокси, разрыв, недоступный процесс) или ответ не пришёл, ID может отсутствовать. Коды не следует включать в общедоступные отчёты вместе с персональными данными.

По умолчанию дополнительная диагностика отключена (`SAFE_DIAGNOSTICS=false`). Явное `SAFE_DIAGNOSTICS=true` включает отдельные строки JSON в stdout **только** для ответов API с кодом 5xx или 429 и для ответов длительностью не менее двух секунд. Строка содержит фиксированные поля: время, случайный ID, грубую категорию маршрута, метод из фиксированного списка, статус, ограниченную длительность и количество пропущенных сигналов. Запросы с другими результатами не журналируются. Нет URL, пути, query, заголовков, IP, тела запроса, cookie, имени, адреса почты, SQL, сообщения исключения или стека. Из-за намеренного отсутствия стека журнал не всегда позволяет выяснить причину сбоя; полноценный безопасный процесс диагностики ещё нужно проектировать.

Лимит — 20 записей за 60 секунд на процесс, остальные пропускаются. Поле `suppressed` появится в следующей фактически записанной строке после обновления окна; если такой строки не будет или процесс перезапустится, счётчик будет потерян. Несколько процессов имеют независимые бюджеты. Это **не** полный журнал, счётчик запросов, защита от атак, метрики, аудит действий или гарантия обнаружения инцидента. Сбой обработчика журнала не должен менять ответ пользователю.

В Compose значение передаётся в API из переменной окружения. Включать осознанно только в контролируемой среде после настройки закрытого сбора, ограниченного хранения и уведомлений. Даже псевдослучайный ID, категория и время могут стать персональными данными при сопоставлении с другими источниками. Отдельно проверить PostgreSQL, reverse proxy, CDN, инфраструктурные журналы и средства сбора: этот компонент **не запрещает им** записывать URL со старыми токенами приглашений, тела, IP, заголовки или другие секреты. Запретить или надёжно редактировать такие записи; не отправлять реальные данные в общий demo.

При ошибке сервера или ограничении частоты, если API вернул корректный ID, текущий интерфейс показывает код запроса при входе и в основных обработчиках; некоторые специализированные сообщения пока могут его не показывать. При обращении в поддержку пользователь может сообщить только код и примерное время. Диагностика отключена по умолчанию, поэтому совпадающей записи может не быть. Не просить пароли, cookie, токены, тело запроса или скриншоты с личными данными. Отсутствие ID или записи ожидаемо, в том числе из-за фильтра и ограничения частоты. Доступ, хранение и передача таких сведений должны быть согласованы с ответственным за данные.

## Готовность схемы

API проверяет совместимость списка миграций при старте, по `/ready` и непосредственно перед обработкой каждого `/api/`-маршрута. При обнаруженном несоответствии или ошибке проверки маршрут возвращает `503 {"error":"UNAVAILABLE"}`, а `/ready` — 503; `/health` по-прежнему показывает только живой процесс. Параллельные проверки объединяются, успешный результат между запросами не кэшируется. Если проверка не отвечает четыре секунды, запросы получают отказ; новые проверки не накапливаются, пока исходная не завершится. Если она зависла навсегда, потребуется восстановить соединение или перезапустить экземпляр. Проверка добавляет обращения к БД и задержку; её поведение при ожидаемой нагрузке, истощении пула и недоступной БД ещё необходимо измерить в целевой среде. Лимиты запросов, парсинг и другие ранние стадии могут завершить запрос до этой проверки.

Проверка сверяет лишь журнал миграций, а не целостность объектов или данных. Она не атомарна с выполнением обработчика: несовместимая миграция может начаться сразу после проверки, а уже выполняющиеся запросы продолжаются. Поэтому она **не заменяет** остановку нового трафика, завершение активных запросов, резервное копирование, проверенное обновление и readiness-aware маршрутизацию. Прямой API-порт не должен быть общедоступен. Обновление и откат должны быть проверены на копии данных; при несоответствии схемы нельзя просто принудительно продолжать обработку.

## Проверки

`backend/tests/diagnostics.test.ts` проверяет согласование ID, недоверие входящему заголовку, отсутствие секретов в сформированных строках, ограничение частоты и отказ обработчика журнала. `backend/tests/serving-readiness.test.ts` проверяет блокировку вызова обработчика, восстановление и объединение параллельных проверок. `tests/run-schema-readiness-live.py` создаёт одноразовую БД и проверяет настоящий процесс, изменённый checksum, 503 API, восстановление и безопасную диагностическую строку. Синтетический HTTPS-тест проверяет передачу ID через gateway, показ кода на формах и отказ старых маршрутов в production-конфигурации (для множества тестовых логинов лимит в этом тесте намеренно повышен); он не заменяет реальный TLS, целевую инфраструктуру, нагрузочное испытание или независимый аудит.
